Product Requirements Document (PRD) + Technical Requirements Document (TRD)

Owner: Sr | Client: Kalgi Handicraft (Akshay Patel, Jasdan, Rajkot, Gujarat) Doc version: 2.0 | Date: Sep 2026

PART 1 — PRD

1. Background & Goal

Kalgi Handicraft sells wooden Meenakari-work handicrafts (Chowki/Bajot/Patla, Dry Fruit Boxes, Pooja Articles, Jewellery/Gift Boxes) currently only via IndiaMART. Goal: an independent, SEO-ranked website + a self-serve admin dashboard so the owner can manage products and inquiries without a developer.

2. Users

User Needs
B2B buyer (gift shops, pooja stores, corporate gifting) Browse catalog, see specs/MOQ/price, send bulk inquiry
Retail buyer Browse, see price, WhatsApp/call to order
Site owner (Akshay) / Admin (you) Add/edit/remove products, manage categories, view & respond to inquiries, see basic analytics — all without code

3. Functional Requirements — Public Website

3.1 Pages

Page Requirement
Home Hero + tagline, category tiles (4), featured products (8–12), trust bar (est. 1999, GST, 4.5★ rating, 6+ yrs), testimonials, blog teaser, sticky WhatsApp CTA
Category listing (/wooden-chowki, /dry-fruit-box, /pooja-articles, /jewellery-gift-box) Grid of products, filters (material, size, price range), sort (price, newest), pagination/infinite scroll, category SEO copy block

Contact Form, embedded Google Map, phone/WhatsApp, business hours, address
404 / thank-you page Custom 404; inquiry-submitted confirmation page

3.2 Inquiry flow (core conversion feature)

  1. User submits form (name, phone, email optional, product, quantity, message) or clicks WhatsApp CTA (pre-filled message with product name).
  2. Form submission → saved to DB → email notification to owner → WhatsApp notification (optional, Phase 2) → confirmation shown to user.
  3. Every inquiry appears in the Admin Dashboard in real time.

3.3 Acceptance criteria (samples)

  • Product page loads with image, price, and working WhatsApp link with pre-filled product name.
  • Inquiry form validates phone (10-digit) and required fields before submit.
  • Category filter updates results without full page reload.
  • All pages pass Lighthouse SEO ≥ 90 and are mobile-responsive at 360px width.

4. Functional Requirements — Admin Dashboard (/admin)

Module Features
Auth Email+password login (single/multi admin), protected routes, session/JWT
Dashboard home Stats: total products, total inquiries (this week/month), recent inquiries list, quick "add product" button
Product management List (search/filter/sort), Add, Edit, Delete, Duplicate; fields: name, slug (auto+editable), category, price, unit, material, size, color options, MOQ, description, SEO title/meta, multiple image upload (drag-drop, reorder, set primary), status (draft/published)
Category management Add/edit/delete category, reorder display sequence, category SEO copy
Inquiry management List (filterable by status/date/product), view detail, mark status (New/Contacted/Converted/Closed), add internal notes, export to CSV, delete/archive

Media library Browse/reuse uploaded images across products
Settings Business info (phone, WhatsApp, address, hours) editable — reflects site-wide (footer, contact page, schema) without code change

4.1 Acceptance criteria

  • Admin can add a new product with images and see it live on the public site within seconds (ISR revalidate or on-demand revalidation).
  • New inquiry submitted on the public site appears in dashboard list without manual refresh needed on next load, and triggers an email.
  • Non-technical user (Akshay) can complete "add product" flow in under 3 minutes after a walkthrough.

5. Non-Functional Requirements

  • Mobile-first, LCP < 2.5s, SEO score 90+, WCAG AA basics (alt text, contrast, focus states)
  • Dashboard usable on desktop + tablet (not mobile-critical)
  • Role-based access ready for future (owner vs staff), even if only one role used initially
  • Daily automated DB backup (MongoDB Atlas backup)

6. Out of Scope (Phase 1)

Payments/cart checkout, multi-language, customer accounts, multi-vendor.

Two build options — pick one:

  • A. Single Next.js app (recommended, faster): public pages + /admin dashboard + /api routes all in one Next.js project → deploy as one unit on Vercel. Simpler, less infra to manage.
  • B. Separate Node/Express backend (better if you want a reusable API / mobile app later, more of a "full MERN" portfolio piece): Express + MongoDB API deployed separately (Render/Railway), Next.js frontend + dashboard consume it.

Given this is a portfolio-building opportunity for you as a MERN dev, Option B shows fuller-stack skill (separate API you designed, auth, deployment across two services). Below the TRD is written for Option B; note where it simplifies if you choose A.

9. Data Models (Mongoose)

// Category
{
  name, slug, description, seoTitle, seoDescription,
  image, sortOrder, isActive
}

// Product
{
  name, slug, category: ObjectId(ref: Category),
  priceFrom: Number, unit: String,             // "per piece"
  material, size, colorOptions: [String],
  moq: Number,
  images: [{ url, alt, isPrimary }],
  description: String,
  seoTitle, seoDescription,
  status: "draft" | "published",
  createdAt, updatedAt
}

// Inquiry
{
  name, phone, email,
  productId: ObjectId(ref: Product), productName,  // denormalized for easy listing
  quantity, message,
  source: "form" | "whatsapp",
  status: "new" | "contacted" | "converted" | "closed",
  notes: String,
  createdAt
}

// User (admin)
{
  email, passwordHash, role: "owner" | "staff", createdAt
}

10. API Endpoints

Method Endpoint Auth Purpose
GET /api/products Public List products (filter by category, status=published)
GET /api/products/:slug Public Product detail
POST /api/products Admin Create product
PUT /api/products/:id Admin Update product
DELETE /api/products/:id Admin Delete product
GET /api/categories Public List categories
POST/PUT/DELETE /api/categories/:id Admin Manage categories
POST /api/inquiries Public Submit inquiry (rate-limited)
GET /api/inquiries Admin List/filter inquiries
PATCH /api/inquiries/:id Admin Update status/notes
POST /api/auth/login Public Admin login → JWT cookie
POST /api/upload Admin Image upload → Cloudinary, returns URL

On product create/update: backend also triggers POST {NEXT_PUBLIC_SITE_URL}/api/revalidate?path=/product/[slug] so the public site updates instantly (Next.js on-demand ISR) instead of waiting for a rebuild.

13. Security

  • Admin routes protected by JWT middleware; passwords hashed with bcrypt.
  • Inquiry endpoint rate-limited + basic honeypot/reCAPTCHA to stop spam.
  • CORS restricted to the frontend domain.
  • .env for secrets (DB URI, JWT secret, Cloudinary/email keys) — never committed.

14. SEO Implementation (unchanged from v1, carried forward)

  • generateMetadata() per page; JSON-LD Product + LocalBusiness + BreadcrumbList
  • sitemap.xml, robots.txt, next/image everywhere, semantic headings
  • Google Business Profile + NAP consistency
  • Target keywords: "wooden chowki manufacturer Gujarat", "meenakari dry fruit box wholesale", "pooja bajot online India", "handicraft jewellery box manufacturer Rajkot"
